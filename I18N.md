# Going international

The goal is an app that works in Hebrew, English, Arabic, German, Japanese,
Italian and Spanish without the layout or the numbers being wrong in any of
them. This file is the state of that work: what is done, what is measured, and
what is deliberately still open.

Everything here is counted from `dev/index.html` with the game document
excluded — it is a standalone page with its own `:root`, it never ships in
another language, and it is not touched.

## The four layers

Translation is one of four, and not the one that blocks the others.

1. **Direction** — one `dir` on the document plus logical CSS everywhere.
2. **Strings** — text out of the source and into a dictionary, with ICU plural
   rules (Arabic has six plural forms, Russian three, Hebrew two).
3. **Formats and units** — kg vs lb, kcal vs kJ, 12h vs 24h, date order, digit
   grouping. The layer people underestimate, and the one that makes a fitness
   app wrong rather than merely untranslated.
4. **What must stay LTR even in Hebrew** — numbers, email, codes.

## Layer 1 — direction: done

Before: 232 direction-carrying declarations, 13 logical ones. After: **168
converted**, and the remainder accounted for rather than ignored.

The document is `<html dir="rtl">`, so declarations outside an LTR island were
written meaning RTL. In RTL, `inline-start` **is** the right edge:

| written as | became |
|---|---|
| `margin-right` / `margin-left` | `margin-inline-start` / `margin-inline-end` |
| `padding-right` / `padding-left` | `padding-inline-start` / `padding-inline-end` |
| `border-right` / `border-left` | `border-inline-start` / `border-inline-end` |
| `right:` / `left:` | `inset-inline-start:` / `inset-inline-end:` |
| `text-align:right` / `left` | `text-align:start` / `end` |

**What was left alone, and why it is correct to leave it:**

- **45 bare `left:`/`right:`** that appear as a pair in the same rule.
  `left:0;right:0` stretches a box across, it does not pick a side. Converting
  it would be churn with a chance of error and no gain.
- **8 corner radii.** Every one is a pair — `border-top-left-radius:0` next to
  `border-top-right-radius:0`, flattening a whole edge. Not one of them is
  one-sided, so none needs `border-start-start-radius`.
- **165 `text-align:center`.** Direction-neutral by definition.
- **7 declarations inside a `direction:ltr` island** — the open item, below.

**How it was checked**, since a wrong mapping reverses just as cleanly as a
right one:

- Flatten both versions back to fully-physical and compare: identical. So the
  pass changed the *spelling* of the inline axis and nothing else.
- In the browser, across all 11 screens: every element box and every run of
  text lands on the same pixel. 2,039 comparisons.
- `getComputedStyle` is not sufficient here — it reports `text-align` as the
  keyword that was written, so `start` and `right` read as different while
  painting the same. That is why the check is geometry.

## Layer 3 — formats and units: done

| was | count | now |
|---|---|---|
| `n.toLocaleString()` | 25 | `nfmt(n)` |
| `toLocaleDateString('he-IL')` | 3 | `toLocaleDateString(APP_LOCALE)` |
| `'+w+' ק"ג'` | 6 | `fmtWeight(w)` |

A bare `toLocaleString()` uses **the browser's** locale, not the app's. That is
a bug today and not only a future one: the same number already read differently
on a German phone, and on an Arabic-locale phone a Hebrew screen rendered
`1,234,567.89` as `١٬٢٣٤٬٥٦٧٫٨٩`.

`APP_LOCALE` and `APP_UNITS` now decide, falling back to the language the app is
written in rather than to the device — a Hebrew app showing German digit
grouping is worse than either choice made consistently.

Weight is **stored in kilograms always**; only the display converts, so no
stored number changes meaning when the preference flips. `fmtWeight` does not
round: a stored 62.75 must not become 62.8 just by being displayed.

Verified by asserting all 21 number shapes the app prints and all 7 weight cases
come out byte-identical to the old output under `he-IL`.

## Still open

### The 7 LTR islands — measured in both directions — a markup decision, not a rename

These sit on elements that carry `direction:ltr` so their digits read correctly.
The trap: `text-align:start` and `margin-inline-start` resolve against **the
element's own** direction, so on a `direction:ltr` element they mean *left* —
the opposite of what the page wants. A rename here would silently invert them.

| line | rule | what it is | what it needs |
|---|---|---|---|
| 184 | `.xd-v` | a numeric value | direction on the digits, alignment on the box |
| 200 | `.xd-sets` | `5×10, 5×8` | same, but check mixed content first |
| 961 | `.wk-t` | a weekday label | same |
| 1048 | `.bk-pass` | password input | must stay LTR; alignment should follow the page |
| 1166 | `.dp-min` | a minutes chip | the gap should flip with the page |
| 1270 | `.td-clock` | a clock chip | the gap should flip with the page |
| 7097 | inline | a code block | correct as-is; code is LTR everywhere |

The fix is to stop putting `direction:ltr` and the alignment on the same
element — page direction on the box, `dir="ltr"` on an inner span for the
digits. That is testable only against real LTR content, which does not exist
yet, so it waits for the string work rather than being guessed at now.

### Strings — done

**2,136 runs wrapped, 1,517 distinct keys.** The Hebrew string is its own key,
so `_t()` is the identity function until a language file loads: the Hebrew build
carries no dictionary, a missing translation falls back to readable text rather
than to `fitness.set.add`, and the pass is reversible.

`dev/data/lang/_template.json` holds every key with an empty value. Fill it,
save as `en.json`, call `langLoad('en')`.

**377 strings were refused rather than guessed at**, and the reason matters:

| refused | why |
|---|---|
| 176 | used as a lookup index — `obj['שם']` |
| 80 | the run carries markup characters |
| 78 | sits mid-tag across a concatenation |
| 24 | an object-literal key — `{"גב רחב":"גב"}` |
| 11 | the key would contain its own quote |
| 8 | compared, not shown — `x === 'כן'` |

The first, fourth and sixth are **data, not text**. Translating a lookup key
breaks the program the moment a language loads — and no reversal test can catch
it, because the transform stays perfectly reversible and only the meaning is
wrong. Those need a different treatment: a stable internal identifier with the
Hebrew as its label, which is a data-model change rather than a text change.

### The refusals were right. The acceptances were not.

The table above is a list of strings the pass declined to touch, and every line
of it holds. The damage was on the other side: **seven collections it accepted
were data too**, and nothing in the refusal logic could have seen it, because
each one looks exactly like a list of labels at the point where it is written.
What makes them data is who reads them, thousands of lines away.

| collection | what it is matched against | what broke |
|---|---|---|
| `MU_SECTIONS[].m` | the exercise database, `e.m.indexOf(_exFilter)` | every muscle filter returned nothing |
| `SAY_DERIVED` | Hebrew food names, to rank derived products down | the food search silently stopped demoting them |
| `PLAN_FEELINGS` | the feelings saved on a day; indexes an emoji table | a saved feeling no longer read as chosen |
| `RELATIONSHIP_TYPES` | `p.relationship`, saved on the person | |
| `PEOPLE_PLACES` | `p.place`, saved on the person | |
| `RF_IMPACT` | a saved reflection answer | |
| `WIZ_NAME_OPTS` | the program name already stored | |

**None of it showed in Hebrew.** `_t()` returns its own key when there is no
translation, so all eleven screens compared byte-identical, the reversal test
passed, and the locale pass passed. The breakage existed only in the state the
whole exercise was for. Measured after the fix, with a live translation
installed: filter `חזה` finds **13** exercises, `גב` finds **6**; the same two
under the shipped code found **0** and **0**, while the label read `Chest`.

The fix needs no migration and gives up no translation: **the list goes back to
being data and the `_t` moves to the one place the value is written to the
screen.** Stored stays canonical Hebrew, compared stays canonical Hebrew, only
the label is translated — which is the id/label split the rest of the app gets
for free from having an `id` field. That is also why the other 23 collections
the detector flags are fine: they are objects compared on `.id`, `.v` or `.k`,
and only their captions were ever wrapped.

`tools/find-translated-data.mjs` grew a second pass for this. It reaches the
first hop and stops there honestly: `MU_SECTIONS` travels list → member →
function argument → an `onclick` attribute → a global → `indexOf`, and following
that is dataflow analysis, not pattern matching. So the pass reports collections
to **read**, and the reading is still the work.

Three defects the checks caught, each worth remembering:

- **A regex literal with quotes in it.** `.replace(/['’׳"“”״,.-]/g,'')` opened a
  phantom string in the lexer and desynchronised every region after it.
- **`t()` collided.** `t` is bound as a local in **74 places** in this file, so
  those functions were calling a string. A name is not free because nothing
  declares it at the top level — it is free when nothing shadows it.
- **Object keys became invalid syntax**, which is how the data-versus-text
  problem was noticed at all.

### A language can now be chosen

`langSet(code)`, from a card in the Me screen. It loads the words, flips the
document direction, and repaints whatever is on screen rather than sending the
person home. Direction and locale come from one `LANGS` record so they cannot
drift — an English UI reading right to left is worse than an untranslated one,
because it looks deliberate.

**`data/lang/en.json` is deliberately partial**: 145 entries covering 604 of
2,152 call sites, 28% of everything rendered. A missing key falls back to the
Hebrew — which is the point of using the source string as the key.

The files sit at the repo root, not under `dev/`, because `appBase()` strips
`dev/` on purpose so both published copies read one `data/`, the way they
already share `exercises.json`.

### The one line that made all of it inert

`body` hard-coded `direction:rtl`. **A `dir` attribute on `<html>` loses to a
declaration on `<body>` every time** — so after the whole 168-declaration
direction pass, nothing mirrored at all.

It was invisible until there was a second language to prove it against, which
is the argument for building the switch early rather than saving it for last.

Two different problems were wearing that one declaration:

- **Containers** (`body`, the crop overlay) had no text of their own and were
  only restating the default. They now inherit.
- **Text boxes** are the opposite case. Forcing RTL is wrong in an English UI;
  forcing LTR is just as wrong for someone typing Hebrew into it. The 13 of
  them now use `unicode-bidi:plaintext` — the CSS form of `dir="auto"`.

Measured both ways: in English the "Today" row moves from x=544 to x=35, and
switching back to Hebrew puts it at 544 again — with `body` computing `rtl` by
inheritance rather than by force.

### Word order and plurals — done

`agoText` glued *"לפני"*, the number and *"ימים"* together. English needs
*"3 days ago"*: the same pieces in a different order, which no value for the key
`לפני` could ever repair. **The translatable unit has to be the whole sentence
with a hole in it.**

`_t` now takes variables and fills `{n}` last, so the Hebrew source still works
with no dictionary at all — `_t('לפני {n} ימים',{n:3})` reads *"לפני 3 ימים"*
untranslated.

Once the sentence is one unit, plurals arrive with it. A dictionary value may be
an **object of plural categories** instead of a string:

```json
"לפני {n} ימים": { "one": "{n} day ago", "other": "{n} days ago" }
```

### Hebrew needed a dictionary after all

"The Hebrew is the key, so Hebrew needs no dictionary" holds for every string
except a **counted** one. Replacing a hand-rolled ternary

```js
(left === 1 ? _t('יום') : _t('ימים'))
```

with a single key lost the singular — Hebrew had nothing to select from and said
*"עוד 1 ימים"*. A regression, and it was caught by checking the **boundary**
rather than a middle value.

So `_lang` now starts as a small Hebrew table rather than `null`. Same lookup,
same plural selection, no fetch on the default path; Hebrew simply has a
dictionary with a handful of entries, and everything not in it still falls back
to the key.

**It came out better than the ternary it replaced.** CLDR gives Hebrew three
categories — `one`, `two`, `other` — so the app now says:

| | before | now |
|---|---|---|
| 2 days | לפני 2 ימים | **לפני יומיים** |
| 2 weeks | לפני 2 שבועות | **לפני שבועיים** |
| 2 months | לפני 2 חודשים | **לפני חודשיים** |

A two-branch ternary could not express the dual. Asking `Intl.PluralRules`
instead of hard-coding "1 versus many" got it for free.

`Intl.PluralRules` picks the category for whatever language is loaded, so
nothing in the app knows any language's grammar. Verified that Arabic resolves
all six — `zero one two few many other` — rather than the two English has.

And the Hebrew was wrong on its own terms before any of this: 31 days gave
`Math.round(31/30) = 1` and printed *"לפני 1 חודשים"*, "1 months". That is a
code bug, not a translation one, and it is fixed in the logic.

| | Hebrew | English |
|---|---|---|
| 3 days | לפני 3 ימים | 3 days ago |
| 9 days | לפני שבוע | A week ago |
| 31 days | לפני חודש | A month ago |
| 95 days | לפני 3 חודשים | 3 months ago |

**The same shape applies elsewhere, and there is now a tool that counts it.**
`tools/find-glued-sentences.mjs` reports every place a sentence is assembled
from translated fragments with a value between them.

    node tools/find-glued-sentences.mjs

It started at **67** and is at **1**.

Getting that number honest took three passes. The naive pattern flagged 291,
almost all of them false: an **array of labels** (`['ינואר','פברואר',…]`) puts
two `_t` calls either side of a comma, and so does an **object literal**
(`{sleep:'שינה', work:'עבודה'}`), and a **ternary** chooses between two whole
labels rather than joining them. None of those is glued. Stripping the string
literals out of the gap makes them separable: an object key leaves `work:`, a
ternary leaves `:allGood?`, and a real interpolated value leaves `tot.p`. A
leading or trailing colon is the tell.

The one that is left is deliberate. Line 10475 chains five nested conditionals
into a paragraph; flattening it into keys would produce a combinatorial set of
sentences no translator could hold in their head. It needs the CODE
restructured first — decide the sentence, then translate it — which is a
different change from this one.

### A fourth shape of data wearing text's clothes

Working through the glued sentences turned up strings that were never text at
all. The extraction refused object keys, comparisons and lookup indexes; it had
no way to recognise these two.

**`foodKey()` — a regex replacement value.** The function normalises a food name
so two spellings compare equal, and its own comment says the result *"exists to
be compared"*. The extraction had wrapped the replacements:

```js
.replace(/יי/g, _t('י')).replace(/וו/g, _t('ו'))
```

**The exercise heuristics — a search needle.** `cand.q` holds equipment tags
from the exercise database, Hebrew strings in a JSON file that no language
switch touches. Five places searched them with a translated needle:

```js
if (cand.q.indexOf(_t('מכונה')) >= 0) …
```

In English `_t` returns "machine", the tags are still `מכונה`, and every test
silently becomes false. No error, no crash — the alternatives ranker just stops
preferring machines and `exAltWhy` stops explaining why.

Six needles now match the database instead of the interface. Proven by asking
`exAltWhy` the same question in English: it still returns the specific answer
rather than the generic fallback.

Worth noticing that these lines hold **both kinds of string side by side** — the
needle is data, the returned sentence is text. That is why no rule about
position could have sorted them automatically.

**Finding those by accident was not a plan**, so there is now a detector:

    node tools/find-translated-data.mjs [file]

It looks for a `_t()` result in a position where the string is used rather than
shown — a search needle, a split separator, a replacement value, something
compared, a lookup index, a storage key, an element id.

It is **validated against a revision that had the bugs**, because a detector
that has only ever reported zero is not evidence of anything:

| | |
|---|---|
| `4bb9f4c` (before the fix) | **9 found** |
| today | **0** |

The first version of it reported 7 of the 9. It missed `foodKey`, where the
regex is the first argument to `.replace` and the translated string is the
second — so nothing named "replace" sits just before it. What sits before it is
the end of a regex literal and a comma, which is now its own shape.

**What it cannot see:** a translated string handed to a function that compares
it three calls later. It catches what is visible at the call site, which is
where both real bugs lived.

### Units, and a sweep that lied

A commit asserted that no translatable string contained a unit any more. It was
wrong, and its own check is why: it searched for the **Latin** `kg` and every
Hebrew `ק"ג` went straight past.

Worse, the app spells that two ways — with a straight quote and with a
gershayim — so even a Hebrew search finds half unless it knows to look for both.
That is exactly how `ק״ג נפח` survived a commit whose message said it had fixed
`kg נפח`. Different strings, same meaning, one search.

Eight more places were bypassing the unit layer in two shapes: printing the
**label** directly instead of calling `weightUnit()`, and printing a **number**
in kilograms beside it that `fmtWeight` would have converted. Both halves wrong
together is the only reason it looked consistent.

**Water had no unit layer at all.** Weight got one; volume never did, so every
reading was millilitres regardless. `fmtVolume` now mirrors `fmtWeight` —
stored in millilitres always, converted only for display.

| | metric | imperial |
|---|---|---|
| weight | 102.5 ק"ג | 226 lb |
| volume | 2,500 מ"ל | 85 fl oz |
| advice | העלה ל־65 ק"ג | העלה ל־143.3 lb |

    node tools/find-units-in-strings.mjs

6 against the revision before the fix, **0** now. The bare label is allowed:
`weightUnit()` returns `_t('ק"ג')` and should, because a German build wants to
translate the word — it just must not be welded into a sentence beside a number
nobody converted.

### Homonyms, a cost of the key choice

Using the Hebrew as the key merges words spelled the same. `חזרה` is both *back*
(the navigation button, 16 uses) and *a repetition*. One key, one translation,
two meanings. Translated as "Back" because that is what nearly every occurrence
is — but the collision is real and belongs on the record.

### The 7 LTR islands

Now testable, because real LTR content finally exists: fill a language file,
call `langLoad`, set `dir="ltr"`, and look at the seven rules listed above.

### The chevrons mirror themselves

Worth recording because the first measurement said the opposite.

A synthetic test showed `‹` unmirrored under `dir="rtl"` — but there it sat
next to Latin text, so it was inside an LTR run. In the app the day arrows hold
**nothing but the glyph**, so it is a neutral character in an RTL paragraph, and
Chrome mirrors it: `#btnPrev` contains `‹` in the DOM and **paints as
`›`** on the right-hand side. Verified by zooming into the rendered header,
not by reading the DOM.

So the text chevrons need no work in either direction. What still would is any
directional icon drawn as SVG, where nothing mirrors on its own.

The lesson is the general one: a synthetic probe answers the question you built,
not the question you have. The app had to be looked at.

### The edges of every array were left in Hebrew

The refusal rule that protected lookup keys could not tell `obj['שם']` from the
first element of `['שם', …]` — both put a bracket against a quote. So Sunday and
Saturday stayed Hebrew while Monday through Friday translated, and January and
December did the same. In English the week would have read
*ראשון, Monday, Tuesday … Friday, שבת*.

**92 edges wrapped, 51 distinct strings.** An edge was taken only when its
siblings in the same array were already wrapped — the sibling passed the same
judgement, in the same array, for the same use — and never when the collection
is one `find-translated-data.mjs` still flags. Reversing the patch gives the
file back byte for byte, all 1,132,518 of them.

The detector now knows the difference, and it is one character: a lookup's `[`
follows the thing being indexed — a name, a `)`, a `]` — while a literal's `[`
follows `=`, `(`, `,`, `:` or `return`. It got that wrong twice before it got it
right, both times on `return [`, which ends in a word character and so looks
exactly like `foo[`. Validated by pointing it at the revision that had the
bugs: **30 there, naming all three by name; 23 here**, and the 92 new wraps
added none.

### "7 MSeptember"

Hebrew writes a date as `7 בספטמבר` — the preposition attaches to the month with
no space — so the pass wrapped the preposition alone, as `_t('ב')`. Two things
were wrong with that, and translating the weekday strip showed both at once:

- **`ב` is also Monday's initial.** One key, two meanings, and no translation
  can satisfy both. The stray M came from the strip's answer landing in a date.
- **A preposition is not translatable in isolation.** English has no word where
  ב stands; it says *7 September* or *September 7*. A key that can only be
  replaced by another preposition expresses neither, and cannot reorder.

The date is now one unit, `'{d} ב{m}'`, at all five sites. Hebrew fills it as it
always did, English as `'{d} {m}'`, and a month-first language as `'{m} {d}'` —
measured: `שני, 7 בספטמבר` · `Monday, 7 September` · `Monday, September 7`. The
lone letter is left meaning only Monday.

### Seven more collections that are data

The same class as the seven fixed earlier, found by reading what consumes them
rather than by any check:

| collection | what it is matched against |
|---|---|
| `FOOD_STOP` | words taken from Hebrew food names — a sentence of stop words, `.split(' ')` into a lookup set |
| `RF_ENERGY` `RF_DRAIN` `RF_BODY` `RF_PLANNED` `RF_PROC` `RF_SELFCARE` | the answers already saved on a day, through `rfChipsHTML`'s `sel.indexOf(opts[i])` |

Measured: two answers saved in Hebrew, with a language installed — **2 chips read
as chosen with the lists canonical, 0 with the lists translated**. Every answer a
person had already given would have come back unselected.

`FOOD_STOP` slipped past `find-translated-data.mjs` because the translated string
is the **subject** of `.split()` rather than its argument, so nothing named split
stands before it. The check has that shape now, and finds it on the revision that
had it. Its first version also matched `_t(…):when.replace(` — a ternary, where
the `.replace` belongs to the identifier on the other side of the colon — so only
whitespace and closing parens may separate the call from the dot.

**`RF_PARTS` is deliberately left wrapped.** It fills a `<datalist>`, where an
option's value *is* its label: there is no display half to translate on its own,
so it needs a different answer than the id/label split and guessing at one here
would be worse than writing this down.

### The language switch was half-broken — fixed

`langSet()` sets `_lang` and repaints — it does not reload. But **16 top-level
collections evaluate `_t()` once, at load**, so they still hold the previous
language until the app is restarted. Walked in the browser, installing a language
and calling `langSet('en')`:

| | |
|---|---|
| `_t('ראשון')` | `Sunday` — the function does switch |
| `dayName()` | `שני` |
| `MO_NAMES[8]` | `ספטמבר` |
| `WK_DAYS[0]` | `ראשון` |

Unwrapping the seven above removes seven of the sixteen, since a canonical list
translated at the point of display is re-translated on every render for free.
The rest are genuinely display collections — `STEPS_SRC_NAMES`, `MUSCLE_ROLLUP`,
`CLOSET_SIDE`, `WK_DAYS`, `WK_SLOTS`, `MO_NAMES`, `CONTACT_TYPES`, `RF_PARTS`,
`RF_DAYNAMES` — and need either the same treatment or a registry that rebuilds
them from `langRepaint`. Not started: it is a feature completeness fix, and
mixing it into a correctness pass would make both harder to judge.

**Fixed.** The nine display collections register themselves instead of being
assigned once:

    var RF_DAYNAMES;langOn(function(){RF_DAYNAMES=[…];});

`langOn` runs the function immediately, so load-time order is exactly what it
was — which matters more than it looks. `MUSCLE_ROLLUP` sits between the
functions that use it, and gathering these into one block at the top of the file
is precisely the hoisting mistake that made every date `NaN` in production.
`langRepaint` now runs the registry before painting, because the paint reads
them.

Measured on the painted screen, switching to a stub English file and back:
**8 Hebrew weekday names → 8 English and 0 Hebrew → 8 Hebrew again**, with
`dayName`, `MO_NAMES`, `WK_DAYS`, `WK_SLOTS` and `CONTACT_TYPES` all following.
No errors on either switch.

### The LTR islands, measured

The paired rules were written some time ago; testing them needed a page that is
actually LTR, which is why the item stayed open. Measured now, with a probe that
reproduces the real arrangement — page direction on an ancestor, the class on the
element, a fixed width:

| rule | RTL | LTR | |
|---|---|---|---|
| `.xd-v` | right | left | flips |
| `.xd-sets` | left | right | flips |
| `.wk-t` | right | left | flips |
| `.bk-pass` | right | left | flips |
| `.dp-min` | `margin-left:5px` | `margin-right:5px` | flips |
| `.td-clock` | `margin-right:5px` | `margin-left:5px` | flips |

**All six mirror, and every RTL value is what the app always painted** — so
Hebrew does not move, which was the whole constraint.

Two notes on how it was measured, because the method decided the answer. The
first four were measured as **geometry** — where the ink lands inside the box —
since `getComputedStyle` reports `text-align` as the keyword that was written and
would call `start` and `right` different while they paint the same. The last two
are spaced with a margin rather than aligned, so the ink-side probe asked the
wrong question and reported "same both ways" for both; `margin-left` is a
physical property whose resolved pixels are an honest answer, and read that way
they flip.

`.xd-sets` mirrors the *other* four rather than matching them, and that is right:
`.xd-v` is start-aligned in both directions and `.xd-sets` is end-aligned in both.
The seventh island — the code block in the steps panel — stays `text-align:left`
on purpose. Code reads left to right in every language.

### Reading back what you typed

`unicode-bidi:plaintext` — the CSS form of `dir="auto"` — was already on
**thirteen** rules, and every one of them is an input or a textarea. So typing
*"meeting with Dana"* into a Hebrew app behaved correctly **while you were
writing it**, and this looked done.

The display half was missing. The elements that show it back inherited the
page's direction, so the line hung off the wrong edge and trailing punctuation
jumped to the front — *"?meeting with Dana"*. The words were in the right order,
because bidi reordering handles that on its own; the paragraph was what was
wrong.

**17 display selectors** now take their direction from their own first strong
character, chosen mechanically as `class="X">'+esc(v)+'</tag>` — the whole
content is the person's, nothing else in the element. Anything mixing a label
with a value is excluded on purpose: the entire line would follow whichever came
first.

Measured both ways, because a rule that fixes English by moving Hebrew is not a
fix:

- English in a Hebrew page turns around in **9 of 10** probed; the tenth,
  `.ppl-tname`, is centre-aligned and has no wrong edge to hang off.
- Hebrew is **geometrically identical in all 17** — the same content measured
  with the property active and forced back off gives the same box, the same ink
  width and the same gap on both sides.

Not included, deliberately: `.ex-en` and `.xd-en` are English exercise names that
already carry `direction:ltr` and are correct; `.bk-txt` is the backup blob, not
prose; and database names are not typed here, so the gain is small next to the
risk of moving a layout nobody asked to move.

### The clock

Six places built an `HH:MM` by hand and nothing used `toLocaleTimeString`, so a
reader in a 12-hour locale saw `17:32`. But **most of those six are not display
at all**, and getting that straight had to come first:

- `fmtTime()` is called at **seven meal-logging sites and its result is stored**
  on the meal as `m.time`.
- `nowHHMM()` is compared as a string — `nowHHMM() >= o.time` — which only works
  while both sides are zero-padded 24-hour text.

Neither may be localised: a stored time that depends on the reader's locale
changes meaning when the locale does, and comparing `"5:03 PM"` as a string is
nonsense. Same split that keeps weight honest — **one canonical stored form,
converted only to display.**

`fmtTime` also never padded the hour, so a meal logged at nine was stored `"9:05"`
and sat under `"13:20"` in a column that never lined up. It pads now. Older
records that say `"9:05"` still read correctly, because `fmtClock` parses the
parts rather than the width.

**`timeStyle:'short'` rather than naming the parts**, and that was a measurement
rather than a preference:

| locale | `hour:'2-digit'` | `timeStyle:'short'` |
|---|---|---|
| he-IL | 09:05 · 17:32 | **9:05 · 17:32** |
| en-US | 09:05 AM · **05:32 PM** | **9:05 AM · 5:32 PM** |
| en-GB | 09:05 · 17:32 | **09:05 · 17:32** |
| de-DE | 09:05 · 17:32 | **09:05 · 17:32** |

Naming the parts forces one shape on every language — `05:32 PM` is not
something anyone writes. `timeStyle` asks each locale what it does, which is the
actual question.

**The Hebrew reader sees exactly what they saw before**, verified across five
times: the app used to print the stored string verbatim, and Hebrew convention
is the unpadded hour, so `fmtClock` returns the same characters.

The formatting is done by `dfmt()`, which had been sitting in the file declared
and never called — so this needed no new cache and inherits the reset that
already happens when the language changes.

## Beyond English — what a Japanese reader needs

The goal Asaf stated on 2026-09-07: **a Japanese reader and an American reader
should find the app as smooth as an Israeli does.** Not an app for Israelis with
an English option. Measured what that actually costs, rather than assuming:

**The machinery holds.** `Intl.PluralRules` reports `other` for every count in
Japanese and `_t` picks it correctly — `1日前 · 2日前 · 5日前`. Arabic resolves all
six categories (`one two few few many other`). Numbers and dates follow
`APP_LOCALE` already: `1,234,567.89` and `9月7日月曜日`.

**The surprise: English is the harder language, not Japanese.** Japanese breaks
between characters, so it fits a narrow chip that English cannot:

| component | overflows in |
|---|---|
| `.td-name` | English **and** Japanese |
| `.tb-n`, `.rf-chip` | **English only** |

Japanese runs about 13% wider than the same phrase in English at the same size
(140px vs 124px for *毎日の振り返り* / *Daily reflection*), but wraps where English
has to overflow.

**The font stack named nothing that can draw a kanji.** `Assistant` is loaded with
Latin and Hebrew subsets only and none of the rest is CJK, so Japanese reached the
generic `sans-serif` and the browser chose. It rendered — which is why this is
easy to miss — but the digits and Latin inside a Japanese line still came from
Assistant while the kanji came from elsewhere, so one line was set in two faces.
The CJK families are named now, after Assistant, and a stack is consulted per
character: **Hebrew and Latin measure identically across 32 samples** — four
strings at four sizes and two weights. All system fonts, nothing downloaded.

### Still the dominant gap

**185 of 1,594 keys are answered — 12%.** Everything above is scaffolding. Picking
English today turns the layout, the dates, the numbers and the plurals around
correctly and leaves most of the words in Hebrew.

### The key set had to be cleaned first

A dictionary cannot be written against keys that contradict themselves.

**`ש` meant three things** — Saturday's initial in a weekday strip (6 uses), fat
in a macro line (3), and *seconds* on a rest button, which turned up only because
a guard counted rather than trusted. Saturday is `S`, fat is `F`, seconds is `s`;
one key cannot say all three.

**Four words were split around their own punctuation** — `הלו"ז`, `קק"ל נשרפו`,
and the macro line itself, each handed over as halves that mean nothing apart.

**And one was not a splitting bug at all.** `prevMax + 'ק"'` predates every
string pass: that column has always printed `85ק"`, missing the ג. Reading the
history before touching it is what told the difference. All three such cells are
stored weights, so they go through `fmtWeight` now and convert as well as
naming — `85 ק"ג` metric, `187.4 lb` imperial, where both used to read `85ק"`.

## German shipped, and the two bug classes it exposed

`de.json` is complete and German is the third entry in `LANGS`, with locale
`de-DE` and direction `ltr`. Switching to it is what proved that *a full
dictionary is not a translated app* — most of the screen stayed Hebrew, for two
different reasons, and each is now a check.

### Frozen at load

`node tools/find-frozen-translations.mjs` — **26 collections, now 0.**

A top-level `var X=[ … _t('…') … ]` calls `_t` exactly once, while the page is
booting, before any dictionary has been fetched. `_t` with no dictionary returns
its own key, so the array filled with Hebrew and stayed Hebrew for the life of
the tab. That was the whole כושר hub, the closet, the insight categories, both
stages of the reflection, and the goal and coach wizards.

The cure already existed in the file: `langOn(fn)` runs fn now and again on
every language change. The pass rewrote each declaration as
`var X;langOn(function(){X=…});`, which runs at exactly the old moment;
reversing it returned the file byte for byte. The registry array had to move to
the top of the script, because three of these are declared above `langOn`'s own
line and a `var` hoists its name without its value.

`langRepaint` had the same disease at a larger scale: it painted three things on
the home screen and left seven alone, which is what a fresh load in German
actually looked like. It calls `goHome()` now — the home screen's own paint.

### Never wrapped at all

`node tools/find-unwrapped-hebrew.mjs` — **322 at the start, 221 now.**

Hebrew handed straight to the DOM. No language file can reveal it, because it
has no key to be missing. What counts as wrapped: `_t('…')`, a `data-t="…"`
attribute, the `HE` dictionary's own keys, and a line marked `// i18n-exempt:`.

The first draft of this check reported 335 and was wrong in both directions: it
treated the slashes of `/יי/g` as quotes and swallowed whole functions into one
imaginary string. A `/` starts a regex only where a value may start, and saying
so took the count to a real 322.

What remains is mostly Hebrew that is *data* rather than text — the food-name
parsing vocabulary, the exercise database's muscle and equipment names, the
`todayStr` parser's own words — plus one thing that is neither: **the workout
coach's prompt is written in Hebrew and asks the model to answer in Hebrew.**
An international app has to ask in the language the person is using. That is
its own pass and is not done.

### One Hebrew word, two German words

`בוקר` is the part of the day and the meal; German has Morgen and Frühstück.
A key may now carry a context after a vertical bar — `_t('בוקר|ארוחה')`. Nothing
shows the bar: with no answer `_t` returns the part before it, so the Hebrew app
reads exactly as it did while a translator sees both halves. It is gettext's
`msgctxt`, spelled for a file whose keys are its source text.

### Where German stands

Driven in the browser across all eleven modules: home has one Hebrew string and
the habit screen has two, and all three are Asaf's own words. Every module's
landing screen is fully German. The deeper views — wizards, editors, sheets —
are what the remaining 221 are mostly in.
